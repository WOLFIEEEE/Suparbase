# Phase 1: Data Model

**Feature**: Power-User Data Ops (v0.7) · [spec.md](./spec.md) · [plan.md](./plan.md)

v0.7 introduces **one new database table** (`saved_views`), one new
audit-log access pattern (per-row fan-out for bulk operations), and a
handful of client-side TypeScript types. No changes to any existing
schema or stored value.

## 1. New table: `saved_views`

A per-user, per-connection, per-table named filter + sort + visibility
snapshot.

### 1.1 Drizzle definition (sketch)

To live at `src/server/views/schema.ts`:

```ts
import { index, jsonb, pgTable, text, timestamp, uuid } from "drizzle-orm/pg-core";
import { users } from "./auth";
import { connections } from "../schema/connections";

export const savedViews = pgTable(
  "saved_views",
  {
    id: uuid("id").primaryKey().defaultRandom(),
    userId: uuid("user_id")
      .notNull()
      .references(() => users.id, { onDelete: "cascade" }),
    connectionId: uuid("connection_id")
      .notNull()
      .references(() => connections.id, { onDelete: "cascade" }),
    tableSchema: text("table_schema").notNull(),
    tableName: text("table_name").notNull(),
    name: text("name").notNull(),               // 1..40 chars enforced server-side
    state: jsonb("state").$type<ViewState>().notNull(),
    createdAt: timestamp("created_at", { withTimezone: true }).defaultNow().notNull(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).defaultNow().notNull(),
  },
  (t) => ({
    perTableIdx: index("saved_views_per_table_idx").on(
      t.userId,
      t.connectionId,
      t.tableSchema,
      t.tableName,
    ),
  }),
);

export type SavedView = typeof savedViews.$inferSelect;
```

### 1.2 Migration

To live at `drizzle/0003_saved_views.sql`. One `CREATE TABLE` + one
`CREATE INDEX`. Generated by `drizzle-kit generate`. No data
backfill (table starts empty).

### 1.3 `ViewState` payload

```ts
interface ViewState {
  search?: string;                          // search term applied to text columns
  sort?: { column: string; direction: "asc" | "desc" };
  filters: ChipSpec[];                      // see §3
  hidden?: string[];                        // overrides to analysis.hiddenColumns
}
```

The `hidden` array layers on top of the AI analysis: columns listed here
are hidden *additionally* (or, when the column is already
analysis-hidden, the override means "show this column anyway": a
v0.7.1 nice-to-have, not in scope for v0.7's minimum).

### 1.4 Constraints

- 5 custom views maximum per `(user_id, connection_id, table_schema, table_name)`.
  Enforced at the API layer in the POST handler: counts existing rows
  before inserting; returns `400 constraint` with `column: "name"` if
  over the limit. The "All" default view is **not** stored; it's
  rendered by the UI as the absence of a custom view.
- `name` length 1..40, NOT NULL, trimmed before insert.
- `state.filters` validated against the Zod schema in §3 before insert
  to catch malformed chips early.
- `ON DELETE CASCADE` from both `users` and `connections` so a user
  deletion or connection deletion takes their views with them.

## 2. Audit log fan-out pattern (existing table, new access pattern)

Existing `audit_log` shape is unchanged. v0.7 introduces one new write
pattern: bulk operations produce N audit rows (one per affected primary
key) in a single transaction.

```text
bulk-delete on 30 rows
   ▼
src/server/proxy/bulk.ts
   ├─ chunk PKs into groups of ≤500
   ├─ for each chunk:
   │     ├─ SELECT snapshots for undo
   │     ├─ DELETE via PostgREST `?pk=in.(...)`
   │     └─ INSERT INTO audit_log
   │           (user_id, connection_id, schema_name, table_name,
   │            primary_key, verb, http_status, created_at)
   │           SELECT $1, $2, $3, $4, json_build_object('pk', pk), 'delete', 200, now()
   │           FROM unnest($5::jsonb[]) pk
   ▼
30 audit_log rows committed in one transaction
```

The single-row endpoint already runs `INSERT INTO audit_log` per row;
bulk reuses the same `recordAuditWrite()` helper, called once per
affected PK in the chunk.

## 3. Filter chip: `ChipSpec`

URL- and state-serializable filter shape. Defined in
`src/lib/filters/types.ts`.

```ts
export type FilterOperator =
  | "eq" | "neq"
  | "like" | "ilike"
  | "is_null" | "not_null"
  | "in"
  | "gt" | "lt" | "gte" | "lte";

export interface ChipSpec {
  column: string;
  op: FilterOperator;
  value: string | string[] | null;   // null for is_null / not_null; array for `in`
}
```

URL serialization:
- `eq`, `neq`, `gt`, `lt`, `gte`, `lte`, `like`, `ilike` → `filter=col.op.val`
- `is_null` → `filter=col.is.null`; `not_null` → `filter=col.not.is.null`
- `in` → `filter=col.in.(a,b,c)`

Multiple chips repeat the `filter` parameter: matches the existing
PostgREST URL convention.

## 6. Import state machine

```ts
type ImportPhase =
  | { kind: "idle" }
  | { kind: "previewing"; rows: PreviewRow[]; mapping: ColumnMap }
  | { kind: "validating"; rows: PreviewRow[]; mapping: ColumnMap; errors: RowError[] }
  | { kind: "importing"; total: number; done: number; errors: RowError[] }
  | { kind: "done";      summary: ImportSummary }
  | { kind: "error";     message: string };

interface PreviewRow {
  index: number;                 // line number in the source file
  raw: Record<string, string>;   // unparsed source
  coerced: Record<string, unknown> | null;  // null = type error
  cellErrors: Record<string, string>;       // column → error message
}

interface ColumnMap {
  // source column header → target table column name OR "__ignore"
  [source: string]: string;
}

interface RowError {
  index: number;
  column?: string;
  reason: string;
}

interface ImportSummary {
  total: number;
  imported: number;
  skipped: number;
  errors: RowError[];
}
```

This state machine drives the ImportPanel UI. No server-side
representation; the server only sees one chunk at a time as a normal
insert request.

## 7. Bulk request envelope

```ts
interface BulkDeleteRequest {
  primaryKeys: PrimaryKeyValue[];
  /**
   * If true, the response includes the full row snapshots that were
   * just deleted, so the client can offer undo via re-insert.
   * Defaults to true.
   */
  returnSnapshots?: boolean;
}

interface BulkDeleteResponse {
  deleted: number;
  snapshots?: Row[];
}

interface BulkUpdateRequest {
  primaryKeys: PrimaryKeyValue[];
  patch: Record<string, unknown>;   // one or more (column, value) pairs
}

interface BulkUpdateResponse {
  updated: number;
}
```

Both routes inherit error semantics from the existing
`AppError`-shaped responses.

## 8. Relationships diagram

```
┌──────────────────┐
│ BulkBar          │ ─► useBulkDelete ─► /api/v/[id]/rest/[name]/bulk-delete
│ BulkUpdatePanel  │ ─► useBulkUpdate ─► /api/v/[id]/rest/[name]/bulk-update
│ ExportMenu       │ ─► fetch(stream) ─► /api/v/[id]/rest/[name]/export
│ ImportPanel      │ ─► useImport     ─► /api/v/[id]/rest/[name]/import (×chunks)
│ ViewTabs         │ ─► useSavedViews ─► /api/views (CRUD)
│ InlineCell       │ ─► useUpdateRow  ─► /api/v/[id]/rest/[name] (existing)
│ FilterChip       │ ─► URL state     ─► useRows (existing) w/ extra params
└──────────────────┘
                       
saved_views (NEW)              audit_log (existing: fan-out write)
  ▲                              ▲
  │ CRUD by /api/views           │ one row per bulk-affected PK
  │                              │
  └──── per-user, per-table ─────┘
```

No changes to `connections`, `users`, `user_settings`, `schema_analysis`.
The new `saved_views` is the only schema migration. Audit-log writes
keep the same row shape; only the access pattern (per-PK fan-out) is
new.
